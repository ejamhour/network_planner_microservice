# SDK 0.1.56 — Projeto de replanejamento de enlaces

`LinkReplanningProject` prepara um projeto separado a partir de uma topologia
instalada e de uma reconfiguração confirmada. Esta versão aceita apenas o modo
enlace, preserva todos os rádios e requer um dispositivo/interface por site
instalado. Solicitações de subárvore são rejeitadas, sem conversão implícita.

```python
project = LinkReplanningProject("../projects/e13_replanejamento", source=source)
project.prepare(client, geo_base_url="http://features:8080")
project.replan_links(client, geo_base_url="http://features:8080")
```

A preparação usa os estágios existentes do serviço para calcular os custos e
ranks da rede instalada, importando o cache bruto do diagnóstico. Confere que os
pais calculados coincidem com a árvore instalada. Retira somente os enlaces
escolhidos no novo TOML; os pontos ainda conectados ficam fixos com os ranks
acumulados no novo CSV. Nenhum arquivo da origem é modificado. A preparação pode
ser repetida com as mesmas entradas sem substituir resultados já produzidos.

Os postes ficam em CSV separado. `replanning.toml` define perfil, altura,
corredor e parâmetros da busca. Cada estudo recebe apenas os postes dentro do
corredor de seu par de extremos; não é gerado um grafo mesh com todos os postes.
O SDK passou a aceitar candidatos explícitos em `ScenarioSession.plan_mesh_link`
por meio do argumento `poles`; o corpo correspondente já era suportado pela API.

Cada LinkPlanner executa um estudo independente, guarda seu grafo avaliado e
proposta, e amplia o cache local. A consolidação recebe apenas os enlaces
preservados, com seus custos, e os caminhos que atendem ao limite por segmento.
Os únicos acessos externos são os originais. Componentes que continuarem
desconectados permanecem visíveis com os enlaces instalados preservados.

As visualizações mostram a rede preparada, as alternativas efetivamente
avaliadas, a solução de cada par e a rede consolidada. Nesta última, segmentos
novos ficam em laranja, os instalados em cinza e os rádios sem serviço recebem
contorno vermelho, inclusive quando o preenchimento roxo identifica equipamento
associado.

## Seleção de caminhos com qualidade

A validação em AGU-S identificou alternativas avaliadas que atendiam à qualidade
por segmento, mas custavam um pouco mais que o enlace direto inadequado. O
adaptador `MeshLinkPlanner` agora prioriza os caminhos que atendem ao limite e
seleciona o de menor custo entre eles. Se nenhum satisfizer o limite, mantém a
proposta de menor custo para inspeção, explicitamente sem atendimento. O filtro
é aplicado antes do limite de caminhos retornados. A busca continua heurística
e limitada ao número de repetidores configurado; não há garantia de ótimo global.

A alteração usa os mesmos endpoints existentes do microserviço; é necessário
que o processo do serviço carregue o código atualizado de `cisei_lib`. Um teste
regressivo cobre um enlace direto de custo 2,5 e uma alternativa de custo total
2,8 com dois segmentos de 1,4: a alternativa atende ao limite 2 e é escolhida.

O notebook `e13_replanejamento.ipynb` usa somente chamadas ao SDK. O projeto de
diagnóstico continua em `e10_diagnostico`; os novos estudos ficam em
`e13_replanejamento`. A remoção de subárvore permanece fora deste fluxo, para a
abordagem da E10 acordada com o usuário.
